# Backend Architecture

Services, data, routes and contracts. **(planned)** marks designed-but-not-built pieces with their issue.

## 1. Components

```
 ingesta (CronJob ×3) ──upsert──▶ PostgreSQL ◀──Prisma── api ──HTTP──▶ predicciones
   │  AdaptadorDeporte                ▲                    │                │
   ▼                                  └──────── SQL ───────┼────────────────┘
 API-Sports (+ fallbacks, SL-20)                           ▼
                                                     Redis (SL-31)
```

| Service | Process | Port | Responsibility |
|---|---|---|---|
| api | `node dist/server.js` | 3000 | REST API, auth, catalog, aggregates, proxy to predicciones |
| ingesta | `ingesta run <deporte>` (Job) · `ingesta serve` | 8080 (serve) | Batch ingestion per sport, run audit |
| predicciones | `uvicorn predicciones.main:app` | 8000 | Inference, training, model registry |

## 2. Data model

Full description in infra [`docs/modelo-datos.md`](https://github.com/statline-iteso/statline-infra/blob/develop/docs/modelo-datos.md). Source of truth: `services/api/prisma/schema.prisma`. Key points:

- 13 entities (the 12 of the proposal plus `modelo_artefacto`); tables and columns are snake_case (`@@map`/`@map`) because Python writes them with SQL.
- Ids are UUIDs generated by the client (Prisma or `uuid4()` in Python); there are no DB defaults for ids.
- `estadistica_jugador_partido.metricas` is JSONB with a GIN `jsonb_path_ops` index.
- Unique keys used for idempotent upserts: `liga(proveedor, proveedor_liga_id, temporada)`, `equipo(liga_id, proveedor_id)`, `jugador(deporte, proveedor_id)`, `partido(liga_id, proveedor_id)`, `estadistica_jugador_partido(partido_id, jugador_id)`, `modelo_artefacto(modelo_id)`.
- `modelo_artefacto` stores the serialized model bytes (`contenido` BYTEA, `sha256`, `tamano_bytes`), one per `modelo_prediccion`. `modelo_prediccion.artefacto_uri` is `db://<modelo_artefacto.id>` (D-28).

## 3. api

### 3.1 Structure

- `src/app.ts` — `createApp(deps)`: the HTTP composition root (helmet → pino-http → JSON body → metrics → health → routers → 404 → errors). Tests build it with a mocked Prisma.
- `src/server.ts` — loads config (zod), wires Prisma, tokens and metrics, listens, drains on SIGTERM.
- `src/lib/crud.ts` — `createCrudRouter()`: the five standard operations, pagination, validation, `writeGuard`. Each resource router registers its extra routes **before** mounting it so they win over `/:id`.
- `src/lib/standings.ts` — pure standings and form logic.
- `src/routes/` — `health`, `usuarios` (auth + users), `catalogo` (ligas, equipos, jugadores, partidos), `schemas` (zod).
- `src/lib/redis.ts` — `createRedis()`: the ioredis client, created only when `REDIS_URL` is set (§3.5).
- `src/lib/cache.ts` — `createCatalogCache()`: read cache and write invalidation for the catalog (§3.5).
- `src/lib/rate-limit.ts` — `createRateLimiters()`: global `/api` and login limiters with Redis and memory fallback (§3.5).
- `src/lib/metricas.ts` — `createMetricasValidator(dir)`: Ajv (2020-12) over `schemas/<deporte>.schema.json`, compiled once at boot.
- `src/routes/` — `health`, `usuarios` (auth + users), `catalogo` (ligas, equipos, jugadores, partidos), `estadisticas` (box-score lines, batch), `listas` (watchlists), `schemas` (zod).
- `src/routes/` — `health`, `usuarios` (auth + users), `catalogo` (ligas, equipos, jugadores, partidos), `alertas`, `ingestas`, `schemas` (zod).

| `/api/modelos` `?deporte=&tipo=` · `/:id` · `POST /:id/activar` (ADMIN) · `POST /reentrenar` (ADMIN) | read-only CRUD: no writes except these actions; artifact bytes never selected |

**Predicciones proxy (SL-29).** The api forwards the five predicciones calls with `PREDICCIONES_URL` and `PREDICCIONES_TIMEOUT_MS` (default 30000). Request bodies are mapped from camelCase to snake_case explicitly (`partidoIds` → `partido_ids`, `jugadorIds` → `jugador_ids`). The predicciones status and JSON body are passed through unchanged. Connection errors and timeouts answer `503 PREDICCIONES_UNAVAILABLE`; a non-JSON answer answers `502 PREDICCIONES_RESPUESTA_INVALIDA`. Errors from predicciones keep their own codes (`NO_ACTIVE_MODEL` 409, `INSUFFICIENT_DATA` 422, `DB_UNAVAILABLE` 503).

### 3.3 Errors

`{ "error": { "code", "message", "details"? } }`. `AppError` → its status; `ZodError` → 400 `VALIDATION_ERROR`; Prisma `P2025` → 404, `P2002` → 409 `DUPLICATE`, `P2003` (missing reference) → 400 `INVALID_REFERENCE`; body over 1 MB → 413 `PAYLOAD_TOO_LARGE`; anything else → 500 `INTERNAL` (logged, never echoed). Metric errors use `VALIDATION_ERROR` with `details: [{path, message}]` (`path` like `metricas.puntos`).

### 3.4 Auth

JWT HS256 with separate secrets for access and refresh tokens. Claims: `sub` (user id), `rol`. Catalog reads need any valid token; catalog writes need ADMIN (data normally comes from ingestion).

### 3.5 Redis: catalog cache and rate limiting (SL-31)

Redis 7 is optional. Without `REDIS_URL` the api runs with the cache bypassed and rate limits kept in process memory. Any Redis failure degrades to the same behaviour and never fails a request.

- **Client.** `ioredis` with lazy connect, no offline queue (commands fail fast while disconnected), 2 s connect timeout and capped exponential reconnect (200 ms doubling, max 10 s). Closed on SIGTERM. Readiness PINGs with a 500 ms timeout.
- **Catalog cache.** Opt-in per route: list and `GET /:id` of ligas, equipos, jugadores and partidos, plus `/api/ligas/:id/posiciones|calendario`, `/api/equipos/:id/forma` and `/api/partidos/:id/boxscore`. Key: `statline:cache:catalogo:v<version>:GET:<originalUrl>`, TTL `CACHE_TTL_S`. Only 200 bodies are stored; responses carry `X-Cache: HIT|MISS`.
- **Invalidation.** Every successful POST/PUT/DELETE on a catalog route INCRs one catalog-wide version key, so all earlier entries become unreachable at once and expire by TTL. One version instead of per-resource prefixes because standings, form and box scores depend on several resources, and no SCAN is needed. The bump runs before the write response is sent. Writes made directly to PostgreSQL (ingesta) are not seen by the API, so they are visible after at most `CACHE_TTL_S`.
- **Metric.** `statline_cache_requests_total{result="hit|miss|bypass"}`.
- **Rate limits.** `express-rate-limit` with `rate-limit-redis`. Fixed window of one minute per client IP: `RATE_LIMIT_PER_MIN` for all `/api` requests, `RATE_LIMIT_LOGIN_PER_MIN` for `POST /api/auth/login`. Keys are `statline:rl:global:*` and `statline:rl:login:*`. 429 body: `{ "error": { "code": "RATE_LIMITED", ... } }` with draft-7 `RateLimit` headers. If a Redis call fails, the hit is counted in a per-replica memory store, so the effective limit is per replica during an outage.
- **Proxy.** `trust proxy` is `1`: the api sits behind exactly one hop (ingress-nginx), so the client IP is the last `X-Forwarded-For` entry added by ingress. If another proxy is added in front, change this value in `src/app.ts` or the rate limit will count the proxy's IP.

### 3.6 Manual ingestion launcher (SL-30)

`POST /api/ingestas/ejecutar` calls a `LanzadorIngesta` (`src/lib/ingesta-lanzador.ts`, injected into `createApp` as `lanzador`), chosen by `INGESTA_LANZADOR`:

- `deshabilitado` (default): 503 `NOT_CONFIGURED`.
- `kubernetes`: `src/lib/k8s.ts` calls the in-cluster API with the pod's service account (`/var/run/secrets/kubernetes.io/serviceaccount`; `https` module, because Node's fetch cannot pin the cluster CA). It GETs `cronjobs/<INGESTA_CRONJOB_PREFIJO>ingesta-<deporte>` in the pod's namespace (the chart sets the prefix to `<release>-`, e.g. `statline-staging-`; default empty) and POSTs a Job `<cronjob>-manual-<ms>` built from `spec.jobTemplate`, with an ownerReference to the CronJob (`controller: false`, so deleting the CronJob garbage-collects it). Returns 202 `{job}`. Errors: 503 `NOT_CONFIGURED` if the CronJob is missing, 503 `K8S_ERROR` for API failures.

**RBAC required (infra):** the api ServiceAccount needs a namespaced `Role` with `get` on `cronjobs` and `create` on `jobs` in API group `batch`, bound by a `RoleBinding`. Nothing broader is needed.

## 4. ingesta

- `adaptadores/base.py` — `AdaptadorDeporte`: `obtener_partidos(fecha)`, `obtener_estadisticas(partido_id)` (I/O, raw payloads) and `normalizar(…)`, `normalizar_estadisticas(…)` (pure).
- `adaptadores/api_sports.py` — shared client: `x-apisports-key`, retries on 429/5xx with exponential backoff, a per-run request budget (`API_SPORTS_DAILY_QUOTA`, default 95 of the free plan's ~100/day).
- `adaptadores/basquetbol.py` — NBA (league 12). pandas flattens box-score lines, drops DNPs and maps provider fields to schema keys.
- `adaptadores/americano.py` — NFL (league 1, api-american-football). Regroups the per-team `groups[].players[].statistics[]` payload by player and category (`"12/20"` made/attempts strings, `-` and nulls count as 0), drops players without a mapped category, maps to the `pase`/`carrera`/`recepcion`/`defensa`/`pateo` groups. Field names are from documentation (D-24), not yet checked against a live response.
- `adaptadores/balldontlie.py` — NBA fallback (balldontlie.io API v1; `/games?dates[]`, `/stats?game_ids[]`, cursor pagination). Same normalized output as `basquetbol.py`, ids namespaced `balldontlie:`. Needs `BALLDONTLIE_API_KEY`. D-27. On the free tier `/stats` answers 401: the run then stores games without box scores (D-39).
- `adaptadores/thesportsdb.py` — NFL (league 4391) and Liga MX (league 4350) fallback on TheSportsDB v1 (`eventsday.php`). Games and scores only: no player box scores on the free tier. Ids namespaced `thesportsdb:`. D-27.
- `adaptadores/respaldo.py` — HTTP client for the fallbacks (retries 429/5xx/network, request counter, Retry-After) and cursor pagination. Exhausted retries raise `ProveedorCaidoError`.
- `adaptadores/con_respaldo.py` — `AdaptadorConRespaldo` wraps the API-Sports adapter with one fallback. On `CuotaAgotadaError`, `ProveedorCaidoError` or `PlanSinAccesoError` (the key's plan does not cover the request, D-38) it switches to the fallback for the rest of the run. `ejecucion_ingesta.proveedor` records the providers used (`api-sports+balldontlie`). D-26. `crear_adaptador` returns it only when `FALLBACK_HABILITADO` is true and a fallback is configured (NBA needs `BALLDONTLIE_API_KEY`).
- `adaptadores/futbol.py` — Liga MX (api-football v3, league 262, `/fixtures` and `/fixtures/players`). Plain Python walks the nested team → players → statistics[0] payload, maps the fixture status codes, parses `league.round` into `jornada` and keeps nulls out of `metricas` (required keys default to 0). Field mapping built from the documentation, see D-25.
- `ejecutor.py` — one run (uses `partidos_del_dia` / `lineas_del_partido`, which the composite overrides): record `EN_CURSO`, walk each day of the range, upsert games, fetch box scores only for `FINALIZADO` games, validate each line (invalid lines are skipped and counted), finish with `EXITOSA`/`FALLIDA`. Quota exhaustion keeps what was stored.
- `repositorio.py` — psycopg upserts on the unique keys of §2, one transaction per game and per line.
- `cli.py` — `ingesta run <deporte> [--desde] [--hasta]` (defaults: yesterday and today, UTC); exit 1 on failure.
- `demo.py` + `cli.py` `seed-demo` — **dev only**, see the note below.

> **Demo data (dev only).** `ingesta seed-demo --confirmar` fills the database with synthetic data for local development (§4). It records provider `demo` in `ejecucion_ingesta` and uses `demo-` prefixed provider ids for teams, players and games, so real rows are never overwritten. Games attach to the seeded `api-sports` league row (`pnpm --filter @statline/api db:seed` must have run). CronJobs never run it.

## 5. predicciones

FastAPI app with `/healthz`, `/readyz`, `/metrics`, and the request contract (`schemas.py`). Requests are snake_case; **responses are camelCase** so the api proxy passes them through (D-34). Every request opens its own PostgreSQL connection in autocommit mode (D-33). Only the api reaches these routes.

| Route | Request | Response (200) |
|---|---|---|
| `POST /pronosticos/generar` | `{deporte, jornada?, partido_ids?}` | `{deporte, modeloId, generados, pronosticos:[{id, partidoId, probLocal, probEmpate, probVisita, marcadorEsperadoLocal, marcadorEsperadoVisita}]}` |
| `POST /proyecciones/generar` | `{deporte, jornada?, jugador_ids?}` | `{deporte, modeloId, generados, proyecciones:[{id, jugadorId, partidoId, metricas}]}` |
| `GET /precision?deporte=&tipo=` | query | `{deporte, tipo, modelo:{id, version, nombreMetrica, metricaError}, precision}` |
| `POST /modelos/reentrenar` | `{deporte, tipo}` | `{modeloId, version, deporte, tipo, nombreMetrica, metrica, baseline, nTrain, nTest, activado, motivo}` |
| `POST /modelos/{id}/activar` | — | `{modeloId, activo: true}` |

Errors use `{error:{code, message, details?}}`: `NO_ACTIVE_MODEL` 409 (generate or precision with no active model), `INSUFFICIENT_DATA` 422, `NOT_FOUND` 404 (unknown or non-UUID model id), `ARTEFACTO_INVALIDO` 500, `DB_UNAVAILABLE` 503, `VALIDATION_ERROR` 422.

- **Generate pronosticos:** scheduled games (filtered by `partido_ids` and/or `jornada`, default all, max 500) get team features from finished games plus the scheduled ones. Forecasts are replaced per (game, model). NBA and NFL store `prob_empate = 0`.
- **Generate proyecciones:** each player on a team of a selected game gets one row for his earliest selected game. `metricas` is a flat object keyed by the metric name, NFL groups dotted (`{"pase.yardas": 241.3}`), D-34. Re-running replaces rows per (player, game, model).
- **Precision:** over the active model's stored rows and finished games. Outcomes: `n` (games with a class; NBA/NFL ties excluded), `aciertos`, `accuracy` (argmax), `logLoss`. Projections: `n` (player-game pairs) and `porObjetivo.<metric>` = `{n, mae}`.
- **Synchronous:** all endpoints answer 200 after the work is done. Training (`/modelos/reentrenar`) can exceed the api timeout (30 s by default); the api then answers 503 while predicciones may still finish. Raise `PREDICCIONES_TIMEOUT_MS` for the first training run.

### 5.2 Team features (`features_partidos`)

For each game, the home team and the away team each get features computed only from their finished games **strictly before** the game's date (no leakage; a game's own result never enters its features):

| Feature | Definition |
|---|---|
| `puntos_favor`, `puntos_contra` | mean points scored/allowed over the last N = 10 games |
| `tasa_victorias` | win rate over the last N games |
| `tasa_victorias_local`, `tasa_victorias_visita` | win rate over the last N home / away games (the home/away split) |
| `dias_descanso` | days since the last game, capped at 14 (NaN without history) |

The vector is `local_<rasgo>`, `visita_<rasgo>` and `dif_<rasgo>` (local minus visita). NaN (no history) is imputed inside each pipeline.

### 5.3 Player features (`features_jugadores`)

Per player line, from that player's last N = 10 lines before the date: `prom_<obj>` (rolling average of each target), `minutos_prom`, `es_local` (home flag), and `rival_<obj>_permitido`: the mean over the rival's last N games of what it allowed (the rival's total of each metric in each of those games, i.e. the opponents' totals).

### 5.4 Models and targets

| Tipo | Model | Targets / classes | Baseline | Metric (lower is better) |
|---|---|---|---|---|
| `RESULTADO_PARTIDO` | `Pipeline(SimpleImputer, StandardScaler, LogisticRegression)` + two `PoissonRegressor` (expected score) | NBA and NFL: `L`, `V` (ties dropped). Futbol: `L`, `E`, `V` | class priors of the training part | `log_loss` on the last 20 % of games by date |
| `PROYECCION_JUGADOR` | one `Pipeline(SimpleImputer, GradientBoostingRegressor)` per target | NBA: `puntos`, `rebotes`, `asistencias`. NFL: `pase.yardas`, `carrera.yardas`, `recepcion.yardas`. Liga MX: `goles`, `asistencias`, `tiros` | the player's rolling average (training mean without history) | `mae`, averaged over targets; per-target `mae_<obj>` and `baseline_mae_<obj>` in the detail |

The time holdout is a date cut: the first 80 % of distinct dates train and the rest validate, so one game never lands on both sides (D-30). Both families need a minimum of data; too little raises `DatosInsuficientesError` (outcome: 60 usable games and every class in the training part; player: 200 lines and 50 rows per target).

### 5.5 Registry and activation

- `registrar`: one transaction inserts `modelo_prediccion` (client UUID, `version` = `YYYYMMDDHHMMSS`, suffix `-synthetic` when any training game comes from the demo seeder, `activo = false`) and `modelo_artefacto` (joblib bytes, `sha256`, `tamano_bytes`). `artefacto_uri = db://<modelo_artefacto.id>` (D-28).
- `activar(modelo_id)`: one transaction. It locks the (deporte, tipo) group, then sets `activo = (id = target)` for the whole group. At most one active version per group.
- `entrenar_y_registrar`: trains, registers and activates only under the rule of D-31. It returns a summary dict (`version`, metric, baseline, `n_train`, `n_test`, `activado`, `motivo`).
- `cargar_activo(deporte, tipo, cache_dir)`: reads the active row and its sha256. The bytes come from `cache_dir/<sha256>.joblib` when that file exists and matches the hash; otherwise they are read from `modelo_artefacto`, verified against the stored sha256 (`ArtefactoInvalidoError` on mismatch, nothing cached) and written atomically. `cache_dir` defaults to `/tmp/statline-modelos` and is a cache only: the database is the source of truth.

### 5.6 Tests

No database in unit tests: `tests/fabrica.py` generates deterministic synthetic games (stronger teams win more). The SQL runs in `tests/test_integracion.py` (`-m integration`, needs `DATABASE_URL`, rolls back). The `integration` job of CI runs it against PostgreSQL 16 with the Prisma migrations.

## 9. CI/CD

- **CI** (`ci.yml`, every push and PR): lint, types, unit tests with the 70 % gate, integration tests against PostgreSQL 16, multi-stage image builds, Trivy (fails on HIGH/CRITICAL).
- **CD** (`cd.yml`, pushes to `develop` and `main`, and `vX.Y.Z` tags): builds `linux/amd64` images for `api`, `predicciones` and `ingesta`, pushes them to Docker Hub as `statline/<svc>:<short-sha>` (7 chars) and, on tags, `statline/<svc>:vX.Y.Z`, scans each pushed image with Trivy, then sends a `repository_dispatch` `bump-image` to `statline-iteso/statline-infra`.
- **Environment mapping:** `develop` → staging, `main` and tags → prod. Infra writes the tags into `gitops/charts/statline/values-<env>.yaml`; Argo CD syncs from there. The backend never touches a cluster.
- **Dispatch payload:** `{"event_type":"bump-image","client_payload":{"env":"staging|prod","images":{"api":"<tag>","predicciones":"<tag>","ingesta":"<tag>"},"source_repo":"statline-iteso/statline-backend","sha":"<full sha>"}}`. Tags are `^[0-9a-f]{7}$` or `^v[0-9]+\.[0-9]+\.[0-9]+$`; infra rejects anything else.
- **Secrets:** `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` (push), `INFRA_DISPATCH_TOKEN` (fine-grained PAT, `contents: write` on statline-infra, used only for the dispatch).
